# Приёмка и демонстрация сильного MVP

## Цель и границы

До 06:00 показать воспроизводимый путь: данные → исправленный спрос → прогноз → предложение по поставщику → объяснение → изменение → ручное утверждение → CSV.
Окно работы: 225 минут, с 02:15 до 06:00; отсчёт `T+0` соответствует 02:15.

Роли: **A** — Codex организатора, API/политика запасов/интеграция/приёмка; **B** — данные и прогноз; **C** — Streamlit и пользовательский сценарий. Организатор принимает продуктовые решения и ведёт выступление.

Обязательный объём: один склад, два поставщика, регулярный и проектный спрос, потерянный спрос, сезонность/рост, Safety Stock/ROP, MOQ/упаковки, датированные поступления, арифметическое объяснение, два сценария и ручное утверждение.
Реальной отправки в 1С или поставщику нет. CSV — результат локального согласования, а не доказательство отправки заказа.

Два режима обязательны:

- **Демонстрационные данные:** фиксированный seed, полные синтетические условия, явная маркировка на экране и в экспорте; все функции доступны.
- **Реальные данные / предварительный просмотр:** происхождение и пробелы видимы; неполные строки нельзя утвердить или экспортировать как готовый заказ. Обзор и исследование продаж доступны.

Исходные Excel остаются локально вне Git; путь задаётся настройкой, без абсолютного пути автора в коде. В репозитории — только безопасные синтетические fixtures и описания схем. Не публиковать сырые корпоративные данные или токены в логи/скриншоты.

## Независимая матрица приёмки

Фиксировать результат в `docs/mvp/evidence/acceptance-results.md`: ID, PASS/FAIL/BLOCKED, commit SHA, команда или действия, фактический результат, ссылка на безопасный артефакт. Матрица проверяет поведение, а не повторяет внутреннюю реализацию.

| ID | Вход или изменение | Ожидаемый результат / инвариант | Исполнитель → проверяющий | Доказательство |

| AT-01 | Чистый запуск без сети; два прогона одного seed и снимка | Получены два поставщика и один склад; количество и объяснения совпадают. Изменяемые run ID/время не входят в сравнение бизнес-результата | A → C | Лог запуска и нормализованный diff результатов |
| AT-02 | Повторный импорт того же файла; отрицательная корректировка; пересечение месячного и транзакционного отчётов | Повтор не удваивает спрос; отрицательные значения не превращены в продажи через `abs`; пересекающиеся агрегаты не суммируются с транзакциями. Неизвестная семантика движения — предупреждение/карантин | B → A | Входные строки и сверка итогов |
| AT-03 | MOQ отсутствует/`#N/A`, конфликт SKU, неизвестное преобразование упаковка→метр, нет актуального остатка | Явная причина блокировки; нет молчаливого MOQ/кратности = 1, цены = 0 или использования месячного остатка как текущего. В реальном режиме утверждение/экспорт затронутых строк запрещены | B+A → C | Таблица качества и ответ API на попытку утверждения |
| AT-04 | Поочерёдно изменить историю продаж, категорийную сезонность и устойчивый рост; остальные условия фиксированы | Меняются соответствующие промежуточные компоненты прогноза. Рост не применён дважды; одиночный пик не принят за новый устойчивый уровень | B → A | До/после по компонентам, выбранные контрольные даты |
| AT-05 | Добавить крупный разовый заказ к регулярному ряду; отдельно — устойчивое повышение продаж | Первый автоматически отмечен `suspected_project` с причиной и неопределённостью; регулярный прогноз защищён. Второй не исключён целиком как проект. Проект не удалён и не создаёт вечный запас | B → A | Отдельный набор контрольных истинных меток и результаты детектора |
| AT-06 | Известное синтетическое отсутствие товара с положительным скрытым спросом; контроль — нулевые продажи при наличии | В окне отсутствия оценка потерь положительна и корректированный спрос выше наблюдаемого; in-stock нули не заполняются автоматически. Показаны метод/диапазон; реальный месячный баланс не выдан за журнал stockout | B → C | Контрольная истина отдельно от входа восстановления; график/таблица |
| AT-07 | Для одного SKU добавить своевременное поступление 20; затем передвинуть ETA за горизонт; затем отменить поставку | Своевременная поставка уменьшает необрезанную потребность на 20 в fixture без иных ограничений; поздняя/отменённая её не уменьшает. При ETA после прогнозируемого дефицита показан риск до поступления | A → B | Датированная таблица и ledger трёх прогонов |
| AT-08 | Резерв или проектное выделение уже вычтено из свободного остатка | Повторного вычитания в расчёте нет; проектное выделение недоступно регулярной потребности. Баланс сверяется по базовой UOM | A → B | Малый числовой fixture с ручным ожидаемым балансом |
| AT-09 | Golden fixture ниже; отдельно raw need = 0 и положительная потребность с иными MOQ/кратностью | Golden = 108; нулевая потребность даёт 0 без top-up. Каждый положительный заказ удовлетворяет MOQ и кратности после преобразования UOM | A → B | Ожидаемые значения и результат, включая purchase/base quantity |
| AT-10 | 95% → 99% cycle service при фиксированном распределении, горизонте и остальных условиях | Промежуточный квантиль/буфер не уменьшается. Округлённый заказ может совпасть. Это целевой cycle service, а не измеренный fill rate; MVP-аппроксимация названа явно | A+B → C | Сравнение исходных параметров, SS/ROP/target/raw need/final qty |
| AT-11 | Задержать поставщика в контролируемом ряду с положительным спросом | Защитный горизонт и ожидаемая потребность согласованно пересчитаны; новое время прихода/риск видимы. Нельзя обещать строгое увеличение каждой округлённой строки | A+B → C | Сравнение базового и сценарного run при одном seed |
| AT-12 | Открыть объяснение каждой строки, затем изменить допустимое количество покупателем | Сумма подписанных компонентов равна итоговому количеству; ручная дельта и причина видимы. Потерянный спрос не прибавлен повторно после включения в прогноз | A+C → B | Golden ledger и проверка сверки всех строк |
| AT-13 | Сгруппировать предложения; убрать цену у одной строки; задать бюджет в полном fixture | Группы не смешивают поставщиков/UOM; итоговая стоимость только при полном сопоставимом покрытии ценами. При неполных ценах бюджет/экономия недоступны; при поддержанном бюджетном сценарии лимит соблюдён и дефицит объяснён | A+C → B | Экран покрытия цен и сравнение итогов с суммой строк |
| AT-14 | Экспорт до approval; approval v1 → изменение → экспорт v1; затем approval текущей версии | Первые попытки отклонены сервером; изменение снимает approval; только точная текущая утверждённая версия экспортируется. Недопустимое ручное количество и блокирующие данные нельзя обойти через API | A → C | Ответы API, журнал версий и утверждённый CSV |
| AT-15 | Пройти UI: режим → предложение → объяснение → сценарий → изменение → approval → CSV | Понятные loading/error/empty states; сценарий не меняет базовый заказ до явного применения; версия, происхождение и buyer-visible uncertainty сохраняются; CSV совпадает с утверждённым экраном | C → A | Короткая запись или последовательность скриншотов |
| AT-16 | Запустить с другого checkout по README и повторить демо после reset | Нет зависимости от путей автора, сети, ключей, неотслеживаемых fixtures. Reset очищает только локальное demo-состояние и воспроизводит результат; корпоративные raw-файлы исключены из Git | A → B или C | Smoke-протокол чистого запуска, проверка tracked-файлов |

Для AT-05 истина хранится только в тестовом oracle: детектор не получает `is_project`, заранее заданную классификацию или магический ID нужной строки. Для AT-06 истинный латентный спрос также доступен только оценке качества, не алгоритму восстановления. Номер накладной не превращать в фиктивный customer ID.

Временное упрощение прогноза допустимо: прозрачная сезонная базовая модель и документированная оценка неопределённости. Защита от проекта, восстановление спроса и сценарии должны реально пересчитываться, а не переключать заранее подготовленные ответы.

## Golden fixture: заказ на 108 единиц

Изолированный числовой пример для проверки политики и XAI, не утверждение о реальной компании. Здесь поступление наступает до даты потребности; UOM — штуки; все значения являются синтетическими.

| Компонент | Дельта |
|---|---:|
| Базовая потребность на защитном горизонте | +100 |
| Сезонная прибавка | +20 |
| Дополнительная прибавка роста | +10 |
| Страховой запас | +30 |
| Свободный остаток | −40 |
| Своевременное подтверждённое поступление | −20 |
| **Неокруглённая потребность** | **100** |
| MOQ = 108 | +8 |
| Кратность = 12 | +0 |
| **Заказ** | **108** |

Отдельно проверить `108 / 12 = 9` упаковочных шагов. Увеличение свободного остатка до 60 даёт raw need 80, но итог остаётся 108 из-за MOQ: интерфейс обязан объяснить это. Golden проверяет вход policy → выход; сквозные тесты отдельно доказывают работу forecast → policy.

## Пятиминутная демонстрация

| Время | Действие организатора | Что подтверждает |
|---|---|---|
| 00:00–00:30 | Назвать проблему, открыть помеченный синтетический режим; показать два поставщика и один склад | Полный путь решения при прозрачном происхождении данных |
| 00:30–01:15 | Показать регулярный ряд и крупный `suspected_project`, затем восстановление известного stockout | Защита от проекта и оценка скрытого спроса; неопределённость остаётся видимой |
| 01:15–02:00 | Открыть заказ 108 и разложить его по ledger; показать MOQ/кратность и ETA | Каждая единица объясняется; поставки учитываются по времени |
| 02:00–03:00 | Сравнить 95% и 99%, затем задержку поставщика; показать SS/raw need и итог заказа | Реальный пересчёт и осознанный компромисс запас/риск; отсутствие ложного обещания fill rate |
| 03:00–04:10 | Показать недоступный экспорт без approval; утвердить; изменить допустимое количество; показать снятое approval; повторно утвердить и скачать CSV | Человек контролирует точную версию; backend защищает процесс |
| 04:10–04:40 | Переключить реальные файлы: показать продажи/качество и блокировки недостающих параметров | Отличие реального preview от готового заказа; нет выдуманных исходных данных |
| 04:40–05:00 | Назвать следующий шаг: верифицированные остатки/stockout/условия → пилот → 1С | Реалистичный путь в эксплуатацию и честные границы MVP |

Если цены полны, в блоке сценариев можно показать стоимость и бюджет. Если нет, показать количество/риск и «стоимость не рассчитана», не добавлять фиктивную экономию.

## Тайминг приёмки и выпуска

| Момент | Контрольная точка | Действие при отставании |
|---|---|---|
| T+0…20, 02:15–02:35 | Согласованы контракты, fixtures, роли и приёмка; A фиксирует golden | Убрать неоднозначность схем до параллельной разработки |
| T+60, 03:15 | Сквозной synthetic run: B → A → C | Приоритет только проходимому пути; прекратить новые идеи |
| T+150, 04:45 | Все обязательные вычисления и approval проходят через UI | Убрать бюджет при неполных ценах, декоративные графики и сложную модель; обязательные проверки сохранить |
| T+185, 05:20 | **Feature freeze**: общий commit, P0 smoke, список дефектов | Только исправления критического пути, без новых зависимостей/архитектуры |
| T+205, 05:40 | **Release**: AT-01…16 пройдены в заявленной области; README и evidence готовы | Критический FAIL исправляется; неподдержанный optional-сценарий скрывается с явным ограничением |
| T+205…225, 05:40–06:00 | 20 минут: два прогона выступления, reset, резервный показ | Зафиксировать выпуск; не обновлять окружение перед защитой |

Нельзя выпускать «успешную» сборку с неработающим approval, несходящимся ledger, пропавшей маркировкой synthetic или молчаливой подстановкой обязательных параметров. Если такой дефект не устранён, назвать демонстрацию неполной; не выдавать её за готовый MVP.

## Подготовка безопасного демо и доказательств

1. A записывает в README проверенные команды запуска/reset, версии зависимостей и seed; reset затрагивает только явно выделенную demo-БД.
2. C заранее открывает нужные экраны; A прогоняет сценарий без интернета и внешних сервисов.
3. B хранит реальные raw-данные локально; в Git проверяются отсутствие raw-файлов, секретов и конфиденциальных логов. Для коллег — локальная директория из переменной окружения.
4. A сохраняет commit SHA, таблицу приёмки и синтетический CSV; C сохраняет короткую резервную запись. Резервная запись называется записью, а не живым запуском.
5. Организатор говорит «демонстрируем механизм» и «целевой service level». Финансовые проценты — только подписанный иллюстративный сценарий; фактическое снижение капитала/дефицита доказывается позднее пилотом.
