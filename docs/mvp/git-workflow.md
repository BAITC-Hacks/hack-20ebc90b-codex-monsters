# Git, разделение файлов и передача работы

Репозиторий: [BAITC-Hacks/hack-20ebc90b-codex-monsters](https://github.com/BAITC-Hacks/hack-20ebc90b-codex-monsters).

**Текущее указание пользователя: все работают непосредственно в `main`.** Старые указания создавать feature branches, worktree или PR отменены. Не создавать новые ветки; не использовать force-push и не переписывать историю.

## Старт и синхронизация

На своём компьютере участник использует отдельный обычный clone, текущая ветка — `main`. Перед изменениями проверить:

```bash
git status --short
git branch --show-current
git fetch origin
```

Если checkout чистый, `main` не имеет локальных расходящихся commits и может быть обновлён без конфликтов:

```bash
git pull --ff-only origin main
```

Если есть незакоммиченная работа, не переключать ветку и не перезаписывать файлы. Сначала выделить и проверить свои изменения. Если локальные и удалённые commits разошлись, согласовать интеграцию с A и объединить актуальный `origin/main` обычным merge в `main`, сохранив обе стороны; не заменять это reset или force-push. Не повторять push вслепую после отказа non-fast-forward.

В общей локальной папке изменения видны всем агентам сразу: не выполнять одновременно commit/pull/merge, не сбрасывать staging другого агента. Владелец A координирует локальные операции Git.

## Владение

| Исполнитель | Область |
|---|---|
| A | `src/ekt/contracts`, `planning`, `api`, `storage`, общие fixtures, зависимости/lock, корневые конфиги, CI, README, integration tests |
| B | `src/ekt/data`, `src/ekt/forecast`, `tests/data`, `tests/forecast`, `scripts/profile_sources.py`, `scripts/build_snapshot.py` |
| C | `apps/buyer_ui`, `tests/ui`, `docs/demo`, `assets/demo` |

Shared contracts и зависимости меняет A. B/C передают конкретный запрос на интерфейс или зависимость, не переписывают чужой модуль. Готовый backend опубликован через `ekt.api.app:app`; runtime types — `ekt.contracts`; live схемы — `/docs` и `/openapi.json`.

## Небольшие commits в main

1. Завершить проверяемый checkpoint в своей области.
2. Посмотреть `git status` и diff; добавить в staging только конкретные свои файлы. Не использовать `git add .` без разбора.
3. Запустить проверки своей части и сообщить ограничения.
4. Сделать небольшой commit в `main`, перед push выполнить `git fetch origin` и проверить, не пришли ли изменения других участников.
5. Интегрировать новые commits, не затирая чужие файлы; повторить затронутые проверки. При конфликте shared contracts/lock привлечь A.
6. Отправить обычным `git push origin main` и передать команде commit SHA, готовое поведение и границы.

Не добавлять новые сырые коммерческие данные, БД, выгрузки, секреты и крупные сгенерированные артефакты. Уже опубликованные другим участником архивы не удалять и историю самостоятельно не чистить.

Отсечки исходного плана: **5:20 — прекращение новых функций; 5:40 — release SHA и готовая среда; до 6:00 — репетиция**. Это исходная шкала пользователя, не новый отсчёт при чтении документа.

## Передача результата

```text
Task: B03
Commit: <SHA или ссылка на commit в main>
Работает: <проверяемое действие>
Контракт: 1.0, совместимые дополнения / конкретные изменения
Проверка: <команда и фактический результат>
Ограничения: <данные, неподключённые компоненты, известные случаи>
Нужно от A/B/C: <точный интерфейс или ничего>
Следующий checkpoint: <результат>
```

A отвечает за сквозную интеграцию и release. Каждый участник проверяет свою часть; C дополнительно проверяет живой пользовательский сценарий, B — численные результаты и отсутствие утечки будущего. Статус «commit отправлен» не равен «вся приёмка пройдена».
