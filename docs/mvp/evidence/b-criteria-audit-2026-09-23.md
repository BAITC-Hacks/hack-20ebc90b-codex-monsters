Новая команда `python -m ekt.data.assessment` формирует JSON и Markdown без
SKU, customer/doc identifiers, транзакций или локальных путей в содержимом.
Проверяет hashes, отдельно считает summary/keyed rows, показывает coverage,
блокировки, metadata-only источники и время одного локального запуска.
Сводка пригодна для Git; Parquet и исходные локальные пути остаются локально.
Время одного запуска с неконтролируемым filesystem cache — не SLA.

В `/path/to/extracted-sources` распаковываются уже переданные архивы с их
структурой IEK/Systeme. Путь заменяется локальным; ключи и сеть для расчёта

Не добавлять `var`/Parquet/БД в Git. Assessment поддерживает `--snapshot`
для проверки существующего manifest; без источников полные знаменатели
остаются unknown, а не восстанавливаются из subset.

Синтетический отчёт исполняет production classifier/recovery/baseline,

## Остаточные ограничения и ответы для защиты

- **Почему не обычное среднее?** Разовый крупный документ и недоступность товара
  могут искажать наблюдаемые продажи в разные стороны. Сравнение приведено на
  контролируемой синтетике с одинаковым окном; универсального выигрыша не доказано.
- **Проект точно обнаружен?** Нет: `suspected_project` — гипотеза pending.
  Количество сохраняется в uncertain; подтверждение/отмена — решение закупщика.
- **Все нули восстановлены?** Нет. In-stock zero остаётся нулём, неизвестная
  доступность не превращается в stockout; требуется независимое подтверждение.
- **99% уже достигнуто?** Нет. Это заданный cycle service и нормальная IID
  аппроксимация с unvalidated calibration, не измеренный fill rate.
- **Почему нельзя заказать по реальным Excel?** Не хватает проверенных текущих
  остатков/условий и полноты истории; защитная блокировка — ожидаемое поведение.
- **Что с устаревшей историей?** Сейчас есть `STALE_DEMAND_COVERAGE` и
  `STALE_HISTORY_RECENT_LEVEL_UNAVAILABLE`, но не жёсткий согласованный порог
  блокировки. Нельзя называть такой прогноз актуальным; порог требует политики
  пилота. Это оставшийся риск, а не измеренная свежесть ERP.
- **Сезонность и sigma надёжны?** Используются прозрачные bounded heuristics,
  train-only история и neutral fallbacks. Intermittent/короткая история,
  зависимость ошибок во времени и нестационарность требуют отдельной оценки.
- **Регулярные крупные заказы прогнозируются полностью?** Detector сохраняет
  их regular allocation, но robust cap baseline отдельно ограничивает редкие
  экстремумы. Контрпример B-E02 показывает этот риск занижения; следующий
  численный этап — сопоставить capped/uncapped стратегии на подтверждённых
  повторяемых заказах и временном holdout, без подгонки под один пример.
- **Метрики в API?** `ForecastArtifact.metrics` пока пуст; исполняемый отчёт
  отдельно даёт синтетические метрики. UI не должен показывать их как real accuracy.
- **Можно ли масштабировать?** Архитектурно можно добавлять mappings/поставщиков;
  enterprise readiness, полный IEK импорт и performance SLA не доказаны.
  Следующий пилот: закупщик подтверждает UOM/MOQ/остатки и coverage, команда
  заранее выбирает temporal holdouts, сравнение с текущим процессом и измеримые
  stockout/overstock/time показатели. Целевые числа согласуются, не выдумываются.
- **Raw-файлы в Git?** Раннее AT-16 требовало исключить их. Два архива опубликованы
