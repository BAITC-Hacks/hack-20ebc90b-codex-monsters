# Проверка исходных данных для готового MVP

Проверено 23 сентября 2026 на текущем `main`, Python 3.12.0, Darwin arm64.
Цель — понятный закупщику результат с проверяемым происхождением данных.
Усилены критерии «ценность», «результат и качество», «масштабирование» и
«презентация»: отделены рабочий демонстрационный заказ, реальная диагностика
и условия начала пилота. Реальная экономия и точность здесь не измеряются.

## Что действительно проверено

папок IEK и Systeme electric: **261 274 строки вместе с заголовками и
пустыми строками**, 261 229 непустых. SHA-256 каждой книги совпал с файлом
в соответствующем исходном ZIP в репозитории. Исходники не изменялись.
Ни коммерческие строки, ни локальные артефакты в этот отчёт не включены.

Структурная проверка означает, что файл читается и его содержимое сверено;
она не подтверждает полноту ERP, смысл каждой проводки или готовность всех
строк к автоматическому заказу. Полный реестр файлов и расположение полей —

## Воспроизведённый реальный preview

Команды выполняются из репозитория; путь к родительской папке нужно заменить
на локальный. Поддержаны и обычные имена после unzip, и искажённые macOS
имена. API по-прежнему читает только явно зарегистрированные пути.

```bash
uv run python -m ekt.data.assessment \
  --systeme-root /path/to/sources \
  --as-of 2026-09-22T23:59:59+05:00 \
  --sku-limit 10000 --output-dir var/product-real-readiness

uv run python -m ekt.forecast --snapshot /path/from/assessment/manifest.json
uv run pytest tests/data tests/forecast -q
uv run ruff check src/ekt/data src/ekt/forecast tests/data tests/forecast
```

Лимит передаётся публичным `MappingConfig.options.sku_limit`; стандартное
значение 20 сохраняет быстрый просмотр. Верхний лимит 10 000 включает все
поддержанные товары, а не создаёт отсутствующие. Сборка из Downloads дала
**565 из 565 Systeme SKU**, **76 997 принятых строк**, **315 quarantined**
(302 отрицательных движения с неподтверждённым смыслом и 13 строк без количества).
Кратности есть для 545 SKU; MOQ, текущие остатки, сроки и закупочные цены
автоматически не придуманы. Все 565 товаров сохранены в master, даже когда
короткой истории недостаточно для conditional forecast.

Без допущения о нулевых днях модель выдала **539 рядов × 90 дней**;
26 SKU не имеют хотя бы двух наблюдаемых дней для оценки uncertainty.
У 33 построенных рядов весь положительный спрос пока uncertain — их нужно
классифицировать закупщику. Никакие SKU молча не выданы за готовые к заказу.
Snapshot `465653b2ae13272746dbef0ff25296b6fcd9dc380cab9faae93886dd13defb87`,
forecast `forecast-73bf16268dd1ada0f71ba4f9`, `robust-daily-v1.3`.
Импорт и прогноз заняли 11,543 с в одном локальном запуске; это не SLA.

Для прежнего быстрого лимита 20 результат остаётся 35 912 принятых строк,
9 quarantined и 20 прогнозных рядов. Это 3,54% SKU и 46,45% исходных строк
S08 с SKU; отбор частых товаров не представляет длинный хвост ассортимента.

### Подключённая история IEK

Preset `iek-preview-v1` читает только зарегистрированные S01/S02/S05.
При `sku_limit=10000` он сохранил **2 149 из 2 151 SKU**, **171 470 положительных
отгрузок** и **131 quarantined** (114 неподдержанных движений и 17 без количества).
Два остальных SKU не имеют поддержанной положительной истории, их спрос
не объявлен нулевым. В master отдельно сохранены **1 965 штучных SKU,
112 в метрах и 72 в упаковках**. Разные единицы не суммируются и не
конвертируются автоматически. Проверка регрессии исключает SKU с конфликтующими
единицами и не использует будущие движения при выборе текущего набора.

S01 «Мин. разр. к отгр.» и S05 с датированными колонками поставок остаются
справочными источниками: без подтверждения единицы закупки число нельзя
выдать за готовый MOQ, а срок в заголовке — за гарантированную поставку.
Закупщик вводит purchase UOM, conversion, MOQ, multiple и будущую поставку
в общей форме подготовки заказа. Исторические продажи в метрах не превращаются
в бухты до такой правки.

Snapshot `c92e2013d412b03ab1e1e1d0c86fe9c613ba29b02d1eef887787b4129b83f79b`.
Полный импорт занял 18,401 с в одном локальном запуске; это не SLA.
Адаптер проверен через публичные `SourceManifest`/`MappingConfig` и точные
зарегистрированные пути, без чтения незарегистрированных файлов.

`mode=real_preview`, `quality=degraded`, `can_plan=false`,
`can_approve=false`, `can_export=false`. На неполной истории неизвестные дни
не считаются нулевыми продажами. Это исходное состояние **до ввода закупщиком
остатков, условий и допущений**, а не запрет локального рабочего заказа.

### Локальный заказ с участием закупщика

Для расчёта календарного спроса закупщик может явно принять допущение:
«на указанном периоде дни без импортированных отгрузок считаем нулевыми».
Оно записывается в новом immutable snapshot как `demand_coverage`,
`provenance=override`, с периодом `[start,end)`, списком SKU/складов и причиной.
Реальная история сохраняет `mode=real_preview`; качество остаётся degraded,
а каждый затронутый прогноз содержит `BUYER_DEMAND_COVERAGE_ASSUMPTION`.
Это принятое для локального заказа допущение, не подтверждение полноты ERP.

Проверяемый пример: 10 единиц через день даёт условный preview 10 единиц
на наблюдаемый день. После принятия закупщиком нулевых дней получается
календарный прогноз 5 единиц в день. У соседнего SKU без такого допущения
условный preview остаётся 10. Причина и область правки сохранены, данные
других товаров не изменены. Расчёт без журнала stockout использует наблюдаемый
спрос; потерянный спрос остаётся неизвестным и не объявляется нулевым.

Ввод свободного запаса, MOQ, кратности, единиц закупки, срока, частоты
пересмотра и стоимости — самостоятельные действия закупщика. Неподдержанные
строки истории не возвращаются в расчёт от одного подтверждения условий.
API/UI интеграция A/C должна сохранять эти допущения в предложении и CSV;
локальное утверждение не является отправкой поставщику или действием ERP.

### Проверка реального пользовательского пути через API

В свежем `TestClient` пройден импорт из каталога для обеих групп источников:
Systeme с лимитом 1 сохранил 1 master / 6 130 sales; IEK — 1 master / 8 256 sales.
Каталог содержит все 12 исходных книг. Далее полные снимки (565 и 2 149 SKU)
использованы для отдельных однострочных локальных заказов:

1. Получение списка условий закупки через `GET .../buyer-inputs`.
2. Ввод **явно тестовых предположений** о запасе, сроках, MOQ, кратности,
   стоимости и единицах. Исторические движения остались реальными. Для IEK
   выбран товар с историей в метрах и тестовая конверсия 100 м на единицу закупки;
   это проверка механики, не утверждение о реальной бухте поставщика.
3. Создание нового снимка и идентичный повтор по idempotency key.
4. Расчёт v1.3, положительное предложение, видимое допущение о нулевых днях.
5. Явное утверждение с `acknowledge_assumptions=true` и экспорт CSV.

Оба заказа прошли сценарий; CSV содержит заголовок «ЛОКАЛЬНЫЙ ПЛАН ЗАКУПКИ —
УСЛОВИЯ И ДОПУЩЕНИЯ ПОДТВЕРЖДЕНЫ ЗАКУПЩИКОМ; НЕ ОТПРАВЛЕН», колонку
`real_preview` и одну строку заказа. Тестовые вводы, локальные заказы и CSV
остались только в gitignored `var`, не в состоянии приложения пользователя.
Исходные файлы не изменены; поставщикам ничего не отправлено.

Именно этот реальный smoke обнаружил и помог исправить несовместимость
служебных полей `source_id`/`row_ref` из импорта с `SkuMaster` при подготовке
заказа. Проверка одной синтетической fixture эту ошибку не показывала.

## Что должен подтвердить закупщик перед реальным пилотом

| Данные / решение | Зачем и откуда получить |
|---|---|
| Полнота периода и смысл движений | ERP-владелец подтверждает поставку, возврат, корректировку, отмену и стабильные ID; иначе отрицательные строки изолированы, пропуски неизвестны |
| Текущий свободный запас | Склад подтверждает on-hand, резерв, блокировку, склад и timestamp; месячный начальный остаток не заменяет эту величину |
| Открытые поставки и ожидаемые даты | Нужны ещё не полученные количества и usable ETA; просроченный заказ не гарантирует доступность |
| MOQ, кратность, единицы закупки | Закупщик отдельно подтверждает MOQ и кратность, перевод шт/упак и м/бухта, неделимый квант |
| Срок поставки и частота пересмотра | Условия поставщика/маршрута и календарь закупщика; не восстанавливаются из названия файла |
| Закупочная стоимость и валюта | Нужны для бюджета и денежных сравнений; цены продаж не равны закупочной стоимости |
| Stockout-интервалы и полнота журнала | Для восстановления потерь спроса; отсутствие журнала не означает отсутствие потерь |
| Псевдоним клиента и категория | Для более точной классификации проектов/повторяемости и применимых коэффициентов; номер документа не является клиентом |

Следующий бизнес-шаг: ввести или подтвердить эти поля на выбранном наборе SKU
и сравнить локальное предложение с текущим заказом закупщика. Для подключения
к ERP и отправки поставщикам потребуются проверка свежести, подлинная
идентификация утверждающего и интеграционный протокол. Это граница внешней
интеграции, а не причина отключать локальные расчёт, правку и экспорт.

В интерфейсе закупщик сначала выбирает демонстрацию или реальные данные,
видит покрытие и причины ограничения. Демонстрация проходит полный путь до
CSV с явной маркировкой. Реальные файлы дают проверяемую диагностику и
исходную историю для предложения с явно введёнными условиями закупщика.

## Изменения и проверка

- Исправлено обнаружение имён файлов после macOS ZIP-декодирования; при двух
  подходящих книгах возвращается ошибка неоднозначности, источник не угадывается.
- Отбор SKU теперь учитывает точный timezone-aware `as_of`; более поздние
  отгрузки того же дня не меняют отбор или название SKU в replay.
- Прогноз `robust-daily-v1.3` показывает допущение закупщика о полноте истории
  и применяет его только к указанным SKU/складам. Регрессионный тест проверяет
  численный переход conditional demand 10 → calendar demand 5.
- **141 tests + 15 subtests passed**, Ruff без ошибок. Проверены IEK layout,
  три единицы истории, отрицательные/другие движения, неизменность сырья,
  registry boundary без directory discovery, большой
  лимит через публичный MappingConfig, недопустимые типы лимита, scoped
  допущение, существующие classification/recovery/decomposition/replay tests.
  Полный реальный snapshot/forecast собран, все 12 книг прочитаны заново.
- Работа агента выполнена локально, без отдельной ветки, commit или push;
  публикацию общего пакета и итоговый SHA сообщает интегратор A.

Для A: зарегистрировать S07/S08/S12 с `systeme-preview-v1` и S01/S02/S05
с `iek-preview-v1`, передавать выбранный `sku_limit`; S01 остаётся справочным.
Для C: показывать фактическое покрытие выбранного импорта и
допущения как действия закупщика. Для B: интерфейсы и payload совместимы,
канонические наблюдения не подменены предположениями.
