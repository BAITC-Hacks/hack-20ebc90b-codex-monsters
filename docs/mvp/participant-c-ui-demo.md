Статус: задание C; фактическую готовность UI подтверждает исполнитель C. Backend и общие типы описаны в [status-a.md](status-a.md). Дедлайн: **225 минут, с 02:15 до 06:00**. Участник A — Codex руководителя, backend и интеграция; B — данные и расчёты; C — интерфейс и demo. Имена и GitHub-аккаунты назначает руководитель.

## 1. Результат и границы

Сделать три вкладки Streamlit: **«Заказы», «Сценарии», «Данные/проекты»**. Закупщик должен увидеть предложение поставщику, понять каждую единицу, сравнить сценарий, отредактировать количество с причиной, утвердить конкретную версию и скачать подготовленный backend CSV. Проектная продажа остаётся отдельным видимым фактом, а обычный спрос не загрязняется всплеском.

Основа: [общая архитектура](../architecture-blueprint.md), [данные и ограничения](../source-data-assessment.md), [единые MVP-контракты](contracts.md). Точные поля и маршруты определяет contracts.md; этот документ не создаёт конкурирующий API. При расхождении старого blueprint и MVP-контрактов для реализации этого релиза использовать MVP-контракты.

| C владеет | Содержание |
|---|---|
| `apps/buyer_ui/**` | Три вкладки, клиент API и mock-клиент, форматирование и ошибки |
| `tests/ui/**` | Минимальные проверки критических пользовательских переходов |
| `docs/demo/**` | Runbook, пятиминутный сценарий и результаты проверки |
| `assets/demo/**` | Только синтетические UI-fixtures и материалы демонстрации |

**A владеет:** API, `src/ekt/contracts/**`, состояниями/версиями/approval/export, inventory/constraints, общими зависимостями и lock-файлом, Compose и CI. **B владеет:** ingestion, классификацией, восстановлением спроса, прогнозом и вычислительными fixtures. C запрашивает изменения у владельца, не правит его файлы параллельно.

Обязательные ограничения:

- UI работает только через API; прямого чтения SQLite/DuckDB/Parquet/Excel нет.
- MOQ, кратность, страховой запас, ROP, бюджет и допустимость approval рассчитывает сервер. Не писать вторые формулы в Streamlit.
- `session_state` хранит фильтры, выбранные ID, черновик формы и request key; бизнес-статус approval хранится на сервере.
- Авторизацию задаёт A. Введённое пользователем имя в текстовом поле не является полномочием утверждать заказ.
- Не устанавливать дополнительные UI-библиотеки; без React, сложного CSS, анимаций и новых зависимостей ради красоты.
- Не отправлять заказы поставщикам и не подключать 1С. Выход MVP — утверждённый CSV.
- Не коммитить оригинальные Excel, реальные клиентские данные, `.env` и ключи. Для публичных скриншотов использовать synthetic demo.

## 2. Клиент и минимальная структура

```text
apps/buyer_ui/
  app.py              # три вкладки и текущий контекст
  client.py           # одинаковый интерфейс MockClient и HttpClient
  views.py            # рендер трёх вкладок, можно разделить при необходимости
  formatting.py       # даты/decimal/UOM; без business rules
assets/demo/ui-fixtures/
tests/ui/
docs/demo/
```

Вначале mock по JSON из согласованных контрактов, затем реальный HTTP через тот же интерфейс. Постоянная метка mock-режима: «Демо: имитация API». После включения HTTP ошибка соединения **не переключает** приложение на mock автоматически.

В верхней части видны режим данных, supplier/warehouse scope, `as_of`, snapshot/run и версия предложения. Технические детали можно раскрыть в expander. Принцип: пользователь понимает, к каким данным относится результат, без стены технических ID.

Дробные количества и деньги приходят как decimal-строки по контракту. UI форматирует их для чтения, сохраняя исходные значения в запросах. Не преобразовывать `null` в ноль. Не суммировать метры и штуки в одну карточку «единиц заказано».

## 3. Вкладка «Заказы» — главный рабочий путь

**Список:** поставщик, склад, SKU/название, количество в закупочной UOM, базовая UOM/эквивалент, срочность, стоимость при наличии, статус и warning. Достаточно фильтров supplier и urgency/blocked. Выбор строки по `line_id`, а не позиции после сортировки.

**Детали выбранной строки:**

1. `safety_stock`, `rop`, `raw_need`, recommended/selected quantities, MOQ и multiple — поля API; остаток, своевременная поставка и прогноз показываются в доступных компонентах explanation, без выдуманных отдельных полей.
2. Упорядоченный `explanation`: базовый спрос → сезонность/рост → safety buffer → остаток/поставка → MOQ → кратность → иные корректировки. Сверку ledger проверяет backend; UI показывает полученный итог и сохранённые компоненты. `manual_override_delta` отображается явно.
3. Причины и ограничения: binding constraint, неполные данные, источник и confidence, если они есть. Неаддитивные пояснения не добавляются к количеству второй раз.
4. При готовом payload B — один простой график: наблюдавшийся регулярный спрос, оценённый потерянный спрос, проектный всплеск и прогноз различимы. Если график задерживает живую интеграцию, использовать таблицу этих величин.

**Редактирование:** отдельная форма с новым количеством, закупочной UOM и обязательной причиной. `PATCH` передаёт expected version. Сервер проверяет ограничения и возвращает новую версию; UI не округляет pack самостоятельно. После успеха перечитать предложение и его ledger.

**Утверждение:** показать поставщика, текущую версию, предупреждения и `as_of`; отправить `expected_version` и `content_hash`. Кнопка зависит от top-level `capabilities.can_approve`, `capabilities.reasons` и `warnings`. У export аналогично `capabilities.can_export`. Сервер повторно проверяет роль/версию независимо от UI. В MVP identity задаёт server config, поэтому постоянно видна подпись «демонстрационная учётная запись»; enterprise auth не заявлять.

**Экспорт:** после approval вызвать синхронный `POST /v1/proposals/{id}/export`; получить утверждённые CSV bytes и дать скачать. Backend сохраняет audit/idempotency; отдельные export jobs/endpoints в MVP не нужны. CSV не собирать из видимой таблицы. Ключ сохранять на время одной логической попытки; после timeout сверять/повторять тем же ключом, как определил A.

Изменение утверждённого заказа создаёт неподтверждённую версию. Ранее скачанный файл не становится результатом новой версии. Complete synthetic demo разрешает approval/export с постоянной пометкой DEMO и watermark в серверном CSV. Реальные строки с отсутствующими обязательными terms остаются blocked.

**DoD:** proposal → ledger → edit → new version → human approval → CSV работает через живой API; draft/stale нельзя экспортировать; после reload статус сохраняется на сервере.

## 4. Вкладка «Сценарии»

Сравнивать результат с завершённым base run на том же snapshot, scope и seed. Контролы:

| Контрол | Значение | Условие |
|---|---|---|
| Целевой cycle service | 95% / 99% | Подпись «цель: цикл без дефицита»; это не achieved service и не fill rate |
| Задержка поставщика | +0 / +7 / +14 дней | Семантика ETA/lead time задаётся серверным контрактом |
| Бюджет | Сумма и валюта | Только при `capabilities.budget_available` и проверенной стоимости; synthetic помечается |

Запуск: `POST /v1/scenarios`, наблюдение: `GET /v1/scenarios/{id}`. UI показывает queued/running/succeeded/failed, время и ошибки. Ограниченный polling или кнопка «Обновить статус»; не строить бесконечный блокирующий цикл. На rerun продолжать чтение по scenario ID, а не создавать новый job.

Сравнение «База / Сценарий»: параметры, количество изменённых строк, закупочная стоимость при достоверности, SS/заказ выбранного SKU, серверные warnings. Риск дефицита, потерянная маржа и экономия показываются **только если реально рассчитаны и возвращены API**. Иначе показать отсутствие оценки, а не выдуманный KPI.

Сценарий не меняет базовое предложение и не получает кнопку approval/export. Для применения политики нужен новый operational run и обычный review. Не обещать рост каждой строки при alpha 95→99, если есть связывающий бюджет и перераспределение.

**DoD:** параметры уходят в правильном request; исходный proposal не меняется; результат изолирован; неподдерживаемый budget отключён с причиной; данные сравнения относятся к одной базе.

## 5. Вкладка «Данные/проекты»

**Данные:** `GET /v1/sources`, создание `POST /v1/snapshots` → `GET /v1/jobs/{id}` → `GET /v1/snapshots/{id}`; готовый fixture snapshot ID также может быть задан конфигурацией. Списочного `GET /v1/snapshots` нет. Планирование: `POST /v1/planning-runs` → `GET /v1/planning-runs/{id}`. Показать источники, дату выгрузки, `quality.accepted_rows/rejected_rows`, `quality.issues` и `quality.capabilities`. Snapshot всегда выбран явно; terminal result ведёт к предложениям. Парсинг XLSX и полноценный upload UX вне P0; B импортирует набор штатным способом.

Готовность делить по смыслу: можно прогнозировать / можно рассчитать заказ / можно оценивать деньги / можно утвердить. Колонка в исходнике не доказывает наличие данных: у Systeme вес есть в заголовке, но в проверенных строках пуст. Monthly opening balance не является текущим остатком или точным логом stockout.

**Проекты P0 — read-only таблица:** `GET /v1/planning-runs/{id}/demand-events` с label/cursor/limit. Показать `event_id`, SKU, observed qty, regular/project/uncertain allocation, label, reason и confidence. Дату/документ показывать только если они реально возвращены контрактом; не делать скрытый запрос к БД. Всплеск не удаляется из истории. Если customer IDs отсутствуют, подписать документную классификацию; номер накладной не называть клиентом. Исторический проект не означает новую будущую закупку без подтверждённого commitment.

Демонстрация project injection выполняется через заранее подготовленные B fixtures/runs. Изменение классификации/forecast override из UI — **stretch**, только если A+B успеют серверную версию/audit/new-run semantics. Не добавлять локальную «правку label» ради вида.

**DoD:** real/synthetic различимы; пропуски и блокирующие причины видны; один и тот же показанный проект сохранён в источнике и отделён от регулярного спроса в результате.

## 6. Ошибки и интерфейсные договорённости

A предоставляет примеры: degraded snapshot, job, proposal with ledger, project rows, scenario, approved CSV. B подтверждает смысл показанных чисел. Proposal status только `draft|approved`; job status — `queued|running|succeeded|failed`. Quality — `ready|degraded|blocked` внутри snapshot/run quality; в proposal использовать top-level capabilities/warnings/excluded_lines. Дополнительные поля/маршруты согласуются в contracts.md; C не подменяет их правдоподобными значениями.

| Состояние | UI-поведение |
|---|---|
| Empty | Объяснить следующий шаг: выбрать snapshot или запустить run |
| Нулевой заказ | «Пополнение не требуется», это корректный результат |
| Loading/job running | Стадия/время/ID; прежние результаты не выдаются за текущие |
| `409` stale version/snapshot | Перечитать состояние, сохранить ввод как неподтверждённый черновик; не перезаписывать автоматически |
| `422` constraints/validation | Показать field error/причину, сохранить ввод для исправления |
| `403` / нет действующей сессии | Показать отсутствие полномочий, не имитировать approval |
| Timeout mutation | Не сообщать «готово»; следовать idempotency/reconciliation контракту A |
| Нет цены/UOM/terms | `null` и blocking reason, зависимые действия выключены |
| Сервер недоступен | Явная ошибка/повтор чтения; никакой незаметной подмены mock |

Перед approve/export перечитывать серверное состояние; не использовать устаревший кэш для бизнес-решения. В кнопках учитывать capabilities, но это не замена backend enforcement. Деньги объединять только при совместимых currency/cost basis; при частичном покрытии показать его долю либо скрыть общий финансовый KPI.

## 8. Минимальная проверка и DoD участника C

Не тестировать отступы и каждую подпись. Использовать доступный механизм UI-тестов без установки новых зависимостей; при нехватке времени фиксировать ручную проверку с шагами. A покрывает backend-инварианты, C проверяет, что пользователь видит правильный результат/ошибку.

1. Mock/synthetic/real режим виден; missing values не становятся 0; метры и штуки различимы.
2. Выбор после фильтра/сортировки использует правильный `line_id`; edit payload содержит expected version и reason.
3. Ledger полный и в серверном порядке; displayed selected quantity соответствует серверной версии, ручная правка видна отдельно.
4. Scenario request содержит alpha/delay, base run и поддерживаемый budget; base proposal не меняется.
5. `409`/`422`/`403` отображаются корректно; UI не показывает ложный approval при отказе.
6. Один живой проход: edit → new version → approve → reload → download того же approved CSV.
7. Draft/stale export отвергается сервером и понятно отображается; synthetic файл помечен DEMO.

В `docs/demo/acceptance-report.md`: commit, fixture/snapshot, run ID, steps, expected/actual, pass/fail, ограничения. В `docs/demo/runbook.md`: **фактически проверенная** команда запуска от A, выбор demo snapshot, известные причины блокировки. Скриншоты optional, на synthetic; не заменяют реальный проход. Не заявлять тесты пройденными до запуска.
