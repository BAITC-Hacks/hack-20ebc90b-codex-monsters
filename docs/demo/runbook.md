# Интерфейс закупщика: запуск и рабочий маршрут

Обычный режим подключается к настоящему API и восстанавливает сохранённые планы.
Технические идентификаторы, настройки API и вывод кода не входят в рабочий маршрут.
Имитация API включается только явно для демонстрации.

## Запуск

Из корня репозитория, после установки зависимостей по корневому README:

```bash
.venv/bin/python -m uvicorn ekt.api.app:app --app-dir src --host 127.0.0.1 --port 8000
```

В другом терминале:

```bash
.venv/bin/python -m streamlit run apps/buyer_ui/app.py --server.address 127.0.0.1 --server.port 8501
```

Открыть `http://127.0.0.1:8501`. После обновления Python-модулей перезапустить
обе службы: обычная перезагрузка страницы не всегда очищает импортированные
модули Streamlit. Базу и корпоративные файлы сохранять вне Git.

| Переменная | Назначение |
|---|---|
| `BUYER_UI_MODE` | `http` по умолчанию; `mock` — явная имитация на синтетических fixtures |
| `BUYER_API_URL` | По умолчанию `http://127.0.0.1:8000` |
| `BUYER_API_TOKEN` | Необязательный серверный bearer token; не вводится в интерфейс |
| `BUYER_LOCK_CONNECTION` | `true` закрепляет HTTP и адрес API за конфигурацией сервера |
| `BUYER_DEVELOPER_MODE` | `true` открывает технические контролы для разработчика; по умолчанию скрыты |
| `BUYER_SNAPSHOT_ID`, `BUYER_RUN_ID` | Необязательный явно выбранный контекст; без них UI восстанавливает серверную историю |
| `BUYER_MOCK_QUALITY` | `ready`, `degraded`, `blocked`; только для явного mock |

При token или `BUYER_LOCK_CONNECTION=true` адрес нельзя подменить состоянием
виджетов. HTTP-ошибка никогда не переключает интерфейс на mock. Полномочия
утверждения проверяет backend; локальная конфигурация не является корпоративной
авторизацией.

## Рабочий маршрут

1. Открыть «Данные» → «Подготовить новый план». Выбрать подключённого поставщика
   либо явно подписанный демонстрационный набор. Для реальных данных выбрать
   первые 20, первые 100 или весь поддерживаемый ассортимент.
2. Нажать «Подготовить план закупки». UI сам наблюдает подготовку и расчёт.
   Для готовых данных откроется план. Если реальным данным не хватает условий,
   откроется «Остатки и условия закупки».
3. Выбрать все товары либо найти нужные по названию и артикулу. В таблице
   подтвердить доступный остаток, единицы и пересчёт, точность складского учёта,
   минимальную партию, упаковку, сроки поставки и период проверки.
   Общие условия можно ввести один раз: они заполняют только пустые ячейки.
   Остатки не придумываются; ноль нужно указать явно. Указать ожидаемые поставки
   и дату прибытия, если они есть. Цена и валюта необязательны: без стоимости
   доступны заказ, утверждение и CSV, а денежный итог и бюджет не рассчитываются.
4. Записать источник сведений или обоснование допущений и подтвердить допущение
   истории: дни без записей считаются нулевыми продажами, возвраты и
   неподтверждённые движения не учтены. «Сохранить условия и рассчитать заказ»
   создаёт отдельный снимок и план; предыдущие результаты не переписываются.
5. В «Плане закупки» выбрать поставщика, проверить количество, срочность,
   объяснение и исключённые товары. Изменить количество с обязательной причиной.
   Несохранённую правку можно отменить. Поиск и фильтр не меняют состав заказа.
6. Для реальных данных подтвердить проверку остатков, условий и допущений.
   «Утвердить и подготовить CSV» утверждает просмотренную версию на сервере.
   Скачать полученный серверный файл. В CSV попадают позиции с положительным
   количеством. Приложение не отправляет заказы поставщикам или в ERP.
7. В «Сравнении вариантов» изменить уровень наличия, задержку и доступный бюджет.
   При необходимости применить условия к отдельному новому плану, затем пройти
   обычную проверку и утверждение. Исходный заказ остаётся сохранённым.

Сохранённые планы доступны над навигацией. При смене плана несохранённый ввод
очищается; серверные правки и утверждения остаются. Повторная загрузка страницы
продолжает незавершённый расчёт без нового запуска.

## Ошибки и проверка

Ошибки содержат причину и действие. `409` требует сверить текущую версию;
`422` — исправить поля; `403` — проверить серверную роль. При timeout результат
не объявляется успешным: для подготовки, сохранения условий, расчёта и CSV
сохраняется тот же ключ повторной попытки. Суммы, неизвестные условия и пропуски
не подменяются нулями.

```bash
.venv/bin/python -m pytest tests/ui -q
.venv/bin/python -m ruff check apps/buyer_ui tests/ui
```

AppTest проверяет формы и состояния; `test_live_backend.py` поднимает отдельный
настоящий HTTP backend с временным состоянием и проверяет правку, утверждение,
серверный CSV и сохранность после перезапуска. Успех синтетического сценария
не подтверждает точность прогноза или экономию на данных компании.
