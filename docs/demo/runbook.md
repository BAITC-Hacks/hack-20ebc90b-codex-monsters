# Запуск интерфейса закупщика

Интерфейс реализует часть C из [плана MVP](../mvp/participant-c-ui-demo.md). Доступны локальная имитация API и настоящий backend A через HTTP. Живой путь с сохранением approval/CSV проверен. Обновления B получены из main 2b7dce6: новые расчёты используют подключённый модуль прогнозирования. Ранее сохранённые расчёты fixture-v1 сохраняют прежнее происхождение и соответствующее предупреждение; UI не переименовывает их в результаты новой модели.

## Требования и запуск

Нужны Python 3.11 или 3.12 и Streamlit 1.64.0. Выполнять команды из корня checkout; сначала проверить подходящую версию через `python3 --version`. Проверенное окружение: Python 3.12.14, Streamlit 1.64.0. Общий uv.lock уже содержит эту версию Streamlit; дополнительные UI-библиотеки не нужны. Ниже обычная установка проекта; для командного окружения доступен существующий frozen uv.lock.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e . pytest
.venv/bin/python -m streamlit run apps/buyer_ui/app.py --server.address 127.0.0.1 --server.port 8501
```

Откройте локальный адрес, напечатанный Streamlit. В режиме mock постоянно видны «Демо: имитация API», synthetic provenance и демонстрационная учётная запись. Начальная синтетическая база: snapshot `demo-snapshot`, run `demo-run`, seed `42`, `as_of=2026-09-01T00:00:00+00:00`. Это воспроизводимый исторический контекст, а не текущие рекомендации по закупке.

Доступны три раздела: «Заказы», «Что, если…», «Данные». Основной экран показывает только заказ; настройки подключения открываются кнопкой «Настройки». Подробнее о новом пути — [упрощение интерфейса](ui-simplification.md). Предложения содержат двух синтетических поставщиков и один склад. Для первой позиции исходный заказ — 108 штук; для второй используются бухты и метры. Их количества нельзя суммировать в общий показатель единиц.

## Основной рабочий путь

Выберите поставщика, просмотрите таблицу и при необходимости найдите товар по названию или артикулу. «Проверить или изменить товар» раскрывает выбор позиции, объяснение расчёта и правку с обязательной причиной. Нажмите «Сохранить количество», затем «Утвердить и подготовить CSV» и «Скачать CSV». Несохранённую правку нужно сохранить или отменить. Если после утверждения подготовка файла завершилась ошибкой, доступна отдельная кнопка «Подготовить CSV» для повторной попытки. Для уже утверждённого заказа после открытия новой сессии эта кнопка также подготавливает файл.

## Ограничения локального mock

- Mock использует только безопасные данные из `assets/demo/ui-fixtures/`. Он не читает Excel, SQLite, DuckDB, Parquet или корпоративные источники.
- Mock демонстрирует версии, optimistic concurrency, approval и CSV в памяти текущего экземпляра клиента. Обновление страницы браузера или перезапуск процесса может сбросить данные: это не доказательство серверной персистентности.
- Ручные значения берутся из явно подготовленных fixtures. Для строки `line-tools` поддержаны 0, 108, 120 и 132; для `line-cable` — 0, 2, 3, 4, 5 и 6 бухт. Другой ввод возвращает ошибку, а не запускает скрытую формулу MOQ.
- Сценарии mock подготовлены заранее: 99% и задержка 0; 95% и задержка 7 дней. Они не подтверждают корректность пересчёта участниками A/B. Бюджетные и другие неподдержанные комбинации должны оставаться явно недоступными или завершаться понятной ошибкой.
- Скачанный файл содержит watermark «ДЕМОНСТРАЦИЯ — НЕ ЗАКАЗ ПОСТАВЩИКУ». Его нельзя представлять как заказ для поставщика.

Для чистого повторения демо нажмите «Сбросить локальное демо» в «Настройках». Можно также перезапустить Streamlit и открыть новую сессию. Удалять файлы, чужие рабочие данные или базы данных для reset не требуется.

## Подключение HTTP

В первом терминале запустите backend с отдельным каталогом только для demo:

```bash
EKT_DATA_DIR=/tmp/ekt-buyer-demo .venv/bin/python -m uvicorn ekt.api.app:app --host 127.0.0.1 --port 18000
```

Во втором терминале запустите UI:

```bash
BUYER_UI_MODE=http BUYER_API_URL=http://127.0.0.1:18000 .venv/bin/python -m streamlit run apps/buyer_ui/app.py --server.address 127.0.0.1 --server.port 8503
```

Эти модули и аргументы проверены с `/tmp/codex-ui-mvp-venv/bin/python`. В разделе «Данные» → «Обновить исходные данные»: source `synthetic-demo`, mapping `1.0`, mode `synthetic_demo`, as_of `2026-09-23T00:00:00+00:00` → «Подготовить данные» → обновить статус → «Использовать эти данные» → «Рассчитать заказ» → обновить статус → «Открыть заказы». Generator фиксирует `demo-20260923-v1` и свой replay as_of; UI показывает фактически возвращённый контекст. После `succeeded` предложения доступны в разделе «Заказы».

HTTP-демо содержит двух поставщиков, 15 пригодных SKU и один исключённый SKU без terms. Количества отличаются от golden108 в mock. Сценарии действительно пересчитывают policy при новом cycle service/задержке и бюджете (если capabilities разрешают); исходное предложение не меняется. Для исторических runs с fixture-v1 приближение остаётся явно обозначенным; для новых runs происхождение задаёт ответ API.

Выберите режим HTTP и адрес backend в настройках интерфейса. Клиент нормализует адрес API с `/v1`, использует timeout 10 секунд и не переходит на mock при ошибках сети. Настройки можно задать переменными окружения:

| Переменная | Смысл / значение по умолчанию |
|---|---|
| `BUYER_UI_MODE` | `mock` или `http`; по умолчанию `mock` |
| `BUYER_API_URL` | Адрес backend; по умолчанию `http://127.0.0.1:8000` |
| `BUYER_API_TOKEN` | Необязательный bearer token; только окружение, не поле полномочий пользователя |
| `BUYER_LOCK_CONNECTION` | `true` для публичного демо: только HTTP и серверный `BUYER_API_URL`; по умолчанию `false` |
| `BUYER_SNAPSHOT_ID` | Готовый snapshot ID; в mock `demo-snapshot`, в HTTP нужно выбрать явно |
| `BUYER_RUN_ID` | Готовый run ID; в mock `demo-run`, в HTTP нужно выбрать явно |
| `BUYER_SEED` | Seed сравнения, по умолчанию `42` |
| `BUYER_MOCK_QUALITY` | `ready`, `degraded`, `blocked`; по умолчанию `ready` |

Пример подключения к готовому локальному backend:

```bash
BUYER_UI_MODE=http BUYER_API_URL=http://127.0.0.1:8000 .venv/bin/python -m streamlit run apps/buyer_ui/app.py --server.address 127.0.0.1 --server.port 8501
```

Если backend требует token, передайте его через `BUYER_API_TOKEN`; не сохраняйте token в Git и не показывайте на скриншотах. При наличии token адрес закреплён за `BUYER_API_URL`: поле URL недоступно для редактирования, а серверная проверка не разрешает отправить учётные данные на другой адрес.

Для публичного демо задайте `BUYER_LOCK_CONNECTION=true`. UI использует HTTP даже при локальном значении `BUYER_UI_MODE=mock`; переключатель режима и адрес API недоступны посетителю. Сервер применяет заданный `BUYER_API_URL` независимо от состояния этих полей. Без этой настройки локальный выбор mock/HTTP сохраняется. API остаётся внутренним сервисом; блокировка подключения не является авторизацией пользователя.

Backend предоставляет [маршруты v1](../mvp/contracts.md#4-граница-backend--ui) и demo identity. Для другого экземпляра A предоставляет URL, готовые snapshot/run IDs и seed либо они создаются через UI. UI не выдаёт введённое человеком имя за роль approver.

При подключении другого окружения повторить проверенный маршрут:

1. `/health`, sources и snapshot реально читаются по HTTP; их `mode`, `as_of` и `quality` видны.
2. Planning run достигает `succeeded`, его proposal IDs доступны; выбранные snapshot и run относятся к одному контексту.
3. Изменение с `expected_version` даёт новый draft, ledger содержит ручную дельту и причину.
4. Approval сохраняется на сервере; reload сохраняет approved-версию. Export до approval отвергается сервером.
5. CSV скачивается как неизменённые bytes ответа backend, после сверки текущей версии. Он содержит правильные mode/version/UOM и watermark.
6. Сценарий сохраняет базовое предложение, использует тот же snapshot/scope/seed и возвращает рассчитанный результат. UI не утверждает сценарий как заказ.

## Ошибки и повторные попытки

`409` означает конфликт актуальной версии/содержимого: перечитайте предложение, сохраните введённые значения как черновик и повторно рассмотрите изменение. Не утверждайте автоматически новую версию. `422` требует исправить количество или устранить серверную причину блокировки. `403` требует действующей роли на backend; имя в UI её не заменяет.

Timeout после изменения означает неизвестный результат. Не считать операцию успешной. Для export и других операций с договорённым idempotency key повторная попытка использует прежний ключ и то же тело; новый ключ создаётся только для нового логического действия. Для PATCH/approve сверить серверную версию и статус перед повтором. Недоступность сервера остаётся видимой ошибкой HTTP-режима.

## Проверки

Клиентские проверки используют стандартную библиотеку Python, безопасный локальный HTTP stub и синтетические fixtures:

```bash
.venv/bin/python -m unittest discover -s tests/ui -v
.venv/bin/python -m pytest -q
```

Streamlit AppTest проверяет критический пользовательский путь. test_live_backend.py запускает собственные uvicorn-процессы с временными каталогами и проверяет настоящий HTTP workflow, перезапуск и persistence. Доказательства и границы проверки forecast находятся в [отчёте приёмки](acceptance-report.md). Запуск stub не подменяет LIVE-проверку.
