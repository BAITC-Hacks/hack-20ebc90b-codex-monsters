# Elektrokomplekt — помощник закупщика

Рабочее место закупщика команды CODEX MONSTERS: загрузка истории, подготовка остатков и условий, рекомендации по пополнению, сравнение сценариев, корректировка и утверждённый CSV. Планы и решения сохраняются локально.

Разработка ведётся **непосредственно в `main`**. Не создавать дополнительные ветки, worktree или PR. [Правила совместной работы](docs/mvp/git-workflow.md), [план команды](docs/mvp/README.md), [текущая готовность A и границы интеграции](docs/mvp/status-a.md).

## Быстрый запуск целого приложения

С установленным Docker (на macOS/Windows запустить Docker Desktop):

```bash
docker compose up --build -d
```

Открыть [приложение](http://localhost:8501). Интерфейс подключён к настоящему
API; SQLite, снимки и утверждения сохраняются в Docker volume `ekt-data`.
Остановка: `docker compose down` (без `-v`, чтобы сохранить данные).

Без Docker, с установленным [uv](https://docs.astral.sh/uv/getting-started/installation/):

```bash
uv sync --frozen --python 3.12
uv run python scripts/run_app.py
```

Та же [страница приложения](http://localhost:8501); API и Swagger доступны
на `http://127.0.0.1:8000/docs`. Один `Ctrl+C` останавливает оба сервиса.
Локальные данные сохраняются в `var/`. Запуск не требует секретов. Доступен
синтетический учебный набор; если исходные архивы IEK/Systeme присутствуют
в корне, книги автоматически распаковываются в игнорируемую Git папку состояния.
Для другой папки: `--source-root /path/to/sources` (внутри — `IEK` и `Systeme electric`).
Параметры: `--port` (также `--ui-port`), `--api-port`, `--state-dir`.
Если `uv` установлен через pip, но не найден в PATH, заменить `uv` на `python3 -m uv`.

## Работа закупщика

1. В «Данных» выберите учебный набор, IEK или Systeme Electric. Для реальных
   файлов доступны 20, 100 или все товары с поддерживаемой историей продаж.
2. Для данных компании откройте «Остатки и условия закупки». Выберите товары,
   заполните свободный остаток на дату расчёта, единицы закупки и конверсию,
   MOQ, кратность, срок поставки и период закупки. Можно задать ожидаемое
   поступление с датой; цена и валюта нужны для суммы и бюджета.
3. Укажите основание и примите допущение об истории: дни без записей считаются
   нулевыми продажами, неподдержанные движения и возвраты не восстановлены.
   «Сохранить условия и рассчитать заказ» создаёт отдельный снимок и план.
   Исходные файлы и предыдущие планы сохраняются без изменения.
4. В «Плане закупки» проверьте риски дефицита, объяснение количества и исключённые
   позиции. Изменяйте количество с причиной; ноль исключает позицию из выгрузки.
5. Сравните 95%/99%, задержку и бюджет в «Сравнении вариантов». Применение
   параметров создаёт новый план; прежнее утверждение не переносится.
6. Утвердите проверенную версию и скачайте CSV. Для реальной истории подтвердите
   введённые условия и допущения. CSV содержит наименования, количества,
   единицы, доступные цены, объяснение и допущения. Приложение не отправляет его
   поставщику или в ERP. После правки требуется новое утверждение.

После перезапуска доступны сохранённые планы, правки, подготовленные условия
и утверждения. Для неполных данных интерфейс показывает, что нужно заполнить;
неизвестная цена не мешает локальному заказу, но денежный бюджет без неё не применяется.
Демонстрация помечена отдельно; реальные движения с допущениями остаются
`real_preview` и не выдаются за проверенные текущие данные ERP.

## Публичная ссылка и облачный деплой

Для временного живого демо без регистрации:

```bash
docker compose --profile share up --build -d
docker compose logs tunnel
```

В логах появится HTTPS-ссылка `https://….trycloudflare.com`. Она работает,
пока запущены компьютер, Docker и tunnel; после пересоздания tunnel адрес может
измениться. Остановить только публичный доступ: `docker compose --profile share stop tunnel`.
Это временная публикация локального приложения, а не независимый облачный сервер.

Для работы без ноутбука использовать Dockerfile на Railway или VPS.
Пошаговые настройки, хранение данных и проверка результата —
[инструкция по деплою](docs/deployment.md).

## Раздельный запуск backend и UI для разработки

Нужны Python 3.11–3.12 и установленный `uv`. Из корня репозитория:

```bash
uv sync --frozen
uv run uvicorn ekt.api.app:app --host 127.0.0.1 --port 8000
```

- [Swagger: запросы и примеры схем](http://127.0.0.1:8000/docs)
- [OpenAPI JSON](http://127.0.0.1:8000/openapi.json)
- [Проверка API](http://127.0.0.1:8000/v1/health)

SQLite и локальные артефакты создаются в `./var`; каталог можно изменить переменной окружения `EKT_DATA_DIR`. Параметры перечислены в [.env.example](.env.example). Если нужен другой demo-пользователь или роль, задать `EKT_DEMO_ACTOR` и `EKT_DEMO_ROLE` в окружении перед запуском. Это демонстрационная серверная identity, не корпоративная аутентификация.

Во втором терминале запустить общий интерфейс с настоящим API:

```bash
BUYER_UI_MODE=http BUYER_API_URL=http://127.0.0.1:8000 uv run streamlit run apps/buyer_ui/app.py --server.address 127.0.0.1 --server.port 8501
```

[Открыть приложение](http://127.0.0.1:8501). Создание снимка и расчёта доступно во вкладке «Данные». По умолчанию UI использует настоящий HTTP API. Изолированный mock включается только явно через `BUYER_UI_MODE=mock`; технические настройки доступны через `BUYER_DEVELOPER_MODE=true`.

## Первый расчёт через Swagger

Полный автоматический walkthrough при запущенном backend:

```bash
uv run python scripts/smoke_api.py
```

Команда создаёт синтетический run, проверяет запрет экспорта черновика, правит строку, утверждает новую версию, сохраняет `var/demo-approved.csv` и сравнивает 95%/99%. Поставщикам ничего не отправляется. Для просмотра тех же действий вручную:

1. Открыть `GET /v1/sources`: встроенный источник — `synthetic-demo`.
2. В `POST /v1/snapshots` отправить:

```json
{
  "source_ids": ["synthetic-demo"],
  "mapping_version": "1.0",
  "mode": "synthetic_demo",
  "as_of": "2026-09-23T00:00:00Z"
}
```

3. Читать возвращённый `status_url` до `succeeded` или `failed`. Успешный job содержит `snapshot_id`/`result_ref`. Синтетический набор использует фиксированный replay-момент **2026-09-23T00:00:00Z**.
4. Передать полученный ID в `POST /v1/planning-runs`; задать `policy.service_target: 0.95`, `policy.policy_version: "mvp-v1"` и новый `idempotency_key`. Необязательные ограничения можно оставить незаданными.
5. Читать `status_url`; после успеха открыть `GET /v1/proposals?run_id=...`, затем детализацию предложения. Проверить `mode`, `model_version` в результате run, `warnings`, `excluded_lines` и объяснение количества.
6. Для ручной правки отправить `PATCH /v1/proposals/{id}` с текущей версией, `line_id`, количеством в покупной единице и причиной. Новая версия снова получает статус `draft`.
7. Утвердить точные `expected_version` и `content_hash` через `/approve`. `/export` возвращает CSV только для утверждённой версии; демонстрационный CSV явно помечен **«ДЕМОНСТРАЦИЯ — НЕ ЗАКАЗ ПОСТАВЩИКУ»**.
8. Для сравнения 95%/99% или задержки +7 дней создать `/v1/scenarios` с `base_run_id`. Сценарий не изменяет базовое предложение и не имеет отдельного утверждения/экспорта.

Схемы request/response смотреть в Swagger; Decimal-количества и деньги сериализуются строками. `null` означает неизвестное значение, не ноль.

## Что реализует A

- Runtime-контракты Pydantic и канонические Parquet-артефакты.
- Расчёт страхового запаса, ROP, потребности, MOQ/упаковок и общего бюджета поставщиков.
- Датированные поставки, ранние риски дефицита, исключения проблемных SKU и сверяемый XAI ledger.
- FastAPI, один локальный worker, SQLite, версии предложений, hash, ручное утверждение, CSV и what-if.

**Модули B/C подключены в общей `main`.** Прогноз использует `model_version="robust-daily-v1.3"`. Реальные источники IEK и Systeme проходят путь до локального утверждения после ввода закупщиком недостающих условий. Покрытие и ограничения файлов описаны в [проверке данных](docs/mvp/evidence/product-data-readiness.md). Если пакет forecast отсутствует, синтетический режим имеет явно помеченный интеграционный fallback `fixture-v1`.

## Подключение участников

**B — данные и прогноз:** реализовать публичные функции:

```python
from ekt.data import build_snapshot
from ekt.forecast import build_forecast

# build_snapshot(SourceManifest, MappingConfig) -> SnapshotManifest
# build_forecast(SnapshotManifest, ForecastRequest) -> ForecastArtifact
```

Общие типы — `ekt.contracts`. Прогноз покрывает минимум 90 дней; API увеличивает горизонт под условия закупки и задержку сценария. Расчёт использует календарные дни UTC. Сохраняются дата, seed, происхождение и явные пробелы данных. [Задание B](docs/mvp/participant-b-data-forecast.md).

**C — интерфейс:** использовать только HTTP `/v1/*`, `/docs`, `/openapi.json`. Не читать backend SQLite и не дублировать формулы расчёта. [Задание C](docs/mvp/participant-c-ui-demo.md).

## Проверки и ограничения

```bash
uv run pytest -q
uv run ruff check src apps tests scripts
```

Актуальный протокол сквозной проверки: [готовность продукта](docs/mvp/evidence/product-acceptance.md). Проверки выполняются на Python 3.12; прохождение локальных тестов не означает успешного запуска облачного CI. Исходная матрица приёмки: [acceptance-demo.md](docs/mvp/acceptance-demo.md).

Это локальный MVP: один worker, локальная учётная запись, календарные дни UTC и целевой cycle service level, а не измеренный достигнутый сервис. Бюджет распределяется допустимым жадным алгоритмом без заявления математического оптимума. Нет отправки поставщикам/1С, SSO, многоскладовой оптимизации и производственного SLA. Введённые закупщиком данные и допущения видны в плане и CSV; утверждение фиксирует решение пользователя.

Новые сырые коммерческие выгрузки, локальные БД, экспорты и секреты в Git не добавлять. Уже внесённые другими участниками файлы самостоятельно не удалять и историю не переписывать.
